# Resto V1.1 — architecture et arbitrages

## Point de départ vérifié

V1 stable : `master`, commit `3413bcc3d57a14771c00c9da83b8455701fcbf30`, PR #6 fusionnée. La branche principale est `master`, pas `main`. Aucun `AGENTS.md` dans le dépôt et aucune PR ouverte au démarrage. Les anciennes branches V0.x/V1 ont été examinées ; aucune PR concurrente active. Branche de travail : `codex/resto-v1.1-google-migration`. Aucune fusion automatique.

Le code V1 réel utilise **sauge/encre** (`#31473A`, `#789B84`, `#F4F2EC`, `#202522`) : la palette bleu/vin/blush mentionnée dans la mission ne correspond pas à cette version stable. La V1.1 conserve donc les couleurs existantes et le rouge Michelin `#CB0028`. Elle n’introduit aucune nouvelle palette globale.

Deux contradictions du brief sont résolues en faveur des consignes explicites : **aucun filtre par défaut sur Carte**, y compris pour les envies non notées ; **aucune note, aucun nombre d’avis et aucun avis Google**. Le filtre personnel ≥5 reste sélectionnable dans le panneau, sans changer le barème de notes.

## Services et dépendances

| Service/composant | Rôle | Déclenchement |
| --- | --- | --- |
| Maps SDK for Android | Fond de carte, déplacement, zoom, marqueurs V1, style JSON officiel | Ouverture de Carte, après vérification des services et de la clé |
| Basic Place Autocomplete, Places UI Kit | Suggestions Google multilignes, catégories de restauration par défaut et recherche élargie facultative | Bouton explicite, puis saisie dans le composant Google |
| Places SDK for Android (New) | Requête `fetchPlace` limitée à `ID` et `LOCATION` | Sélection explicite ou bouton Localiser ; jamais toutes les anciennes fiches |
| Place Details Compact, Places UI Kit | Nom et adresse externes, attribution Google conservée | Bouton Informations Google Maps, écran natif dédié |
| Room | Données personnelles, relations, ID Google facultatif, provenance des coordonnées durables | Fonctionnement local existant |
| GoogleCoordinateCache | Coordonnées externes séparées, en mémoire, délai monotone 12 h, maximum 200 points | Réutilisation des requêtes déjà réalisées dans le processus |

La version Places **5.3.0** est la dernière version stable 5.x conservant l’API `fetchPlace` utilisée pour obtenir uniquement les coordonnées. Google annonce 6.0.2 au 30 septembre 2026 avec la suppression de cette API. La migration choisit la branche stable 5.x ; aucune API Legacy n’est initialisée. Maps est fixé à **20.0.0**. Les versions sont fixes, sans `+`.

La compilation CI a confirmé que Places 5.3 contient des métadonnées Kotlin **2.3**, incompatibles avec Kotlin 2.0.21 de la V1. Les outils sont donc ajustés à **Kotlin 2.3.21, KSP 2.3.12, AGP 8.13.2 et Gradle 8.13**. AGP 8.13.2 apporte le R8 compatible Kotlin 2.3. **Room 2.8.5** prend en charge KSP2 ; son utilisation reste Android/SupportSQLite, sans adoption d’un nouveau moteur ou réécriture des DAO. Les tests de migration valident également ce changement de bibliothèque. **Java 17, compile/target SDK 35 et min SDK 26** restent conservés. La désucration Java est activée comme demandé par Places 5.x.

La configuration locale du SDK Places est initialisée au démarrage uniquement lorsqu’une clé est renseignée et que les services sont disponibles, afin de permettre à Android de restaurer une activité Autocomplete après interruption du processus. Aucun chargement de carte, recherche ou requête de lieu n’est attendu pour ouvrir le carnet ; une indisponibilité ne bloque pas les fonctions locales. Les appels de coordonnées sont sérialisés, réutilisent le cache, ont un délai de 12 secondes et propagent correctement l’annulation. La carte conserve sa caméra entre onglets et rotations ; le viewport représente l’état de navigation cartographique et n’est pas un cache de coordonnées de restaurants.

Autocomplete New accepte au maximum cinq types principaux. Ces catégories ne couvrent pas à elles seules tous les types spécialisés (`bistro`, `french_restaurant`, `pub`, etc.). L’option **Élargir la recherche à tous les établissements** retire donc le filtre dans les formulaires, sans ajouter de requête automatique. Le nom saisi et la localisation approximative du composant Google continuent à guider les suggestions. La recherche cartographique est déjà non filtrée par type. Ce choix évite d’assimiler « pas de suggestion avec ce filtre » à « absent de Google » ; il reste à vérifier avec les clés réelles.

## Conformité EEE : décision concrète

Documentation consultée le 11 octobre 2026. Un nouveau projet lié à une facturation française relève des conditions EEE entrées en application le **8 juillet 2025**. Leur notion d’association à une carte inclut les affichages liés et les liens vers une carte : séparer simplement les écrans ne suffit pas.

Le contenu Places API autre que latitude, longitude et place ID est soumis aux restrictions EEE d’association à une carte et d’usages autorisés. Les composants Places UI Kit bénéficient de l’exception prévue aux articles 15.3/16 ; ils conservent leurs attributions, liens et mentions. Cette exception d’affichage **n’autorise pas pour autant le stockage illimité des noms/adresses**. Un bouton « confirmer » ou une correction cosmétique ne transforme pas automatiquement un contenu Google en donnée personnelle librement stockable.

**Le préremplissage permanent du nom/adresse depuis Google n’est donc pas implémenté.** L’utilisateur recherche et associe un établissement, consulte son nom/adresse dans le composant Google et renseigne les champs de son propre carnet. Seul le texte de recherche qu’il a lui-même saisi peut servir de nom initial si le nom personnel est vide. L’adresse personnelle reste requise, comme dans la V1. Les données existantes ne sont jamais remplacées lors d’une association. L’écran Google exclut rating, reviews, type, photos, téléphone et horaires en ne demandant que `Content.ADDRESS` ; le nom et l’attribution intégrés au composant restent visibles.

Les coordonnées Places peuvent être mises en cache **30 jours au maximum**. Pour éviter toute rétention sur disque pendant des mois lorsque l’application n’est pas lancée, Resto V1.1 ne les écrit pas sur disque. Le cache mémoire est limité à 12 h, expiré avant utilisation et vidé à la restauration. Les fiches Google créées sans coordonnées personnelles nécessitent une action **Adresses à localiser → Localiser** après une fermeture complète du processus. Les positions V1, personnelles ou importées restent durables. Ce compromis privilégie la conservation du carnet, la conformité et l’absence de requêtes automatiques coûteuses. Ne pas recopier des coordonnées Google dans le champ « personnel » pour contourner cette distinction.

Le journal hors ligne et la recherche locale n’utilisent que les données personnelles. Sans services Google, Carte explique l’indisponibilité et propose le Journal. Il n’existe aucune garantie de fonds de carte hors ligne, ni de fonctionnement microG : voir le protocole manuel.

## Modèle et migrations

`RestaurantEntity.id` demeure la clé primaire locale. Migration explicite Room **1 → 2** :

- ajout nullable `googlePlaceId` ; index unique facultatif empêchant deux fiches associées au même établissement ; plusieurs `NULL` restent permis ;
- ajout `coordinateSource`, par défaut `LEGACY`, pour les coordonnées V1. Les nouveaux champs manuels utilisent `USER`, les imports peuvent employer `IMPORT` ; la valeur `GOOGLE` est refusée dans les coordonnées durables ;
- conservation de tous les champs, tables, identifiants, clés étrangères et relations ; aucun fallback destructif ;
- `geoapifyPlaceId` et son index restent **des données historiques passives**. Aucune recherche ni configuration Geoapify ne reste active.

ZIP **version 2** exporte les mêmes données personnelles et photographies, plus `googlePlaceId` et `coordinateSource`. Le lecteur accepte versions 1 et 2 ; l’absence des nouveaux champs reçoit `NULL`/`LEGACY`. Le cache Google est structurellement extérieur aux objets sérialisés. La restauration conserve le fonctionnement V1 : remplacement atomique du carnet courant après validation, pas fusion de deux carnets. Les identifiants sont conservés, les archives incohérentes refusées et une seconde restauration ne crée pas de doublons.

## Éléments préservés

Journal, Envies, Statistiques, filtres, types de cuisine normalisés, catégories, barème 1–10, notes existantes et sous-notes, calendrier, plats/prix conservés, photos personnelles (5/visite), édition/suppression, passages Envie/Visité, statistiques Michelin et partage. Aucun backend ni compte utilisateur introduit. Les liens d’itinéraire acceptent désormais l’ID Places facultatif, sans appel API. L’implémentation V1 des autres parcours n’est pas refaite.

MapLibre, les classes de recherche Geoapify et le style OpenFreeMap sont retirés. Le style Maps JSON est local et officiel, sans Map ID Cloud requis. Tous les pins réutilisent le bitmap V1 sauge opaque ; les envies conservent leur signe +. Les POI sont masqués, les noms de rues/quartiers conservés. Resto, les activités Places et la carte restent clairs même en mode sombre Android.
