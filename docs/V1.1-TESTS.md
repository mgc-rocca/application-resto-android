# Resto V1.1 — rapport et protocole de tests

## Statut vérifiable

Ce rapport distingue une inspection, un test exécuté et une validation sur appareil. Les tests Google nécessitent vos propres clés restreintes et une facturation configurée. Aucun appareil Android physique ni Fairphone /e/OS n’est connecté à l’environnement de développement.

| Vérification | Statut initial | Preuve/limite |
| --- | --- | --- |
| Préservation des sept tables par SQL 1 → 2 | Réussie dans SQLite local | Ancien schéma Room exact ; toutes les colonnes V1 comparées ; clés étrangères intactes ; index Google nullable unique testé |
| Format du ZIP V1 de test et validité de la photo | Réussie | Fixture synthétique selon le sérialiseur V1 du commit 3413bcc ; archive et image décodables |
| Style JSON Google | Réussie | JSON analysé ; contrôle de rendu Google encore manuel |
| Références actives aux anciens SDK | Réussie | Classes Geoapify supprimées, dépendance MapLibre retirée, ancien style remplacé ; IDs historiques conservés |
| Compilation et tests Android locaux | Non exécutés | Téléchargement Gradle bloqué : `Network is unreachable` ; aucun SDK Android local exploitable |
| CI : tests JVM, lint, Debug, Release, APK de tests | À exécuter via PR | Workflow prévu ; succès à confirmer par résultats réels |
| CI : migration Room et round-trip ZIP sur Android | À exécuter via PR | Émulateur Android API 35 sans clé ; `connectedDebugAndroidTest` |
| Recherches, carte réelle, clé/quota Google | Non exécutés | Aucune clé ni configuration Cloud utilisateur ; tests manuels requis |
| Fairphone 6 /e/OS 4.0 et microG | Non exécutés | Compatibilité non validée ; protocole ci-dessous |

Les statuts CI seront actualisés si leur exécution est possible. Aucun test bloqué ou non lancé ne doit être présenté comme réussi.

Les premières exécutions [16](https://github.com/mgc-rocca/application-resto-android/actions/runs/38129681608) et [17](https://github.com/mgc-rocca/application-resto-android/actions/runs/38130091060) ont échoué à la compilation Kotlin : le SDK Places 5.3 utilise des métadonnées 2.3 alors que la V1 compilait avec Kotlin 2.0.21. Les outils Kotlin/KSP/AGP/Gradle et Room ont été ajustés aux versions compatibles documentées dans l’architecture. Ces tentatives n’ont pas exécuté les tests Android ; une nouvelle exécution doit valider la correction.

## Tests automatisés ajoutés

`GoogleCoordinateCacheTest` vérifie expiration au seuil, horloge monotone, retour d’horloge, absence de persistance, purge, borne de taille et coordonnées invalides.

`GoogleMigrationTest` ouvre une **base exportée par l’APK V1 stable**, avec restaurants, envie, visite, sous-notes, commentaire, tag, plat/prix et chemin photo. Il ouvre ensuite cette copie par Room 2 avec la migration explicite et compare chaque colonne V1 et chaque relation. Room valide lui-même le nouveau schéma.

`GoogleBackupCompatibilityTest` restaure un **ZIP exporté par l’APK V1 stable**, préserve données et octets de la photo, associe un ID Google sans changer les coordonnées personnelles, exporte en ZIP 2, restaure et compare les tables, restaure une seconde fois sans doublon. Un deuxième test refuse la même association Google sur deux fiches et accepte plusieurs restaurants manuels. Il faut encore tester un ZIP exporté par **votre APK V1 installé** ; les données de référence ne remplacent pas cette validation de votre carnet réel.

Le job `stable-v1-export` compile le commit V1 `3413bcc` avec un test d’export isolé, restaure une donnée d’entrée synthétique, puis utilise **le sérialiseur et Room de cette V1** pour produire `resto-stable-v1.zip` et une base SQLite checkpointée. Le job V1.1 télécharge ces deux fichiers avant ses tests. Ainsi, les données sont fictives, mais l’archive testée et la base sont effectivement produites par la version précédente, et non fabriquées à la main. Le test d’export est dans `tools/compatibility/` et n’entre pas dans l’APK V1.1.

La CI compile également les tests instrumentés. Une compilation de ces tests ne signifie pas leur exécution : le second job lance explicitement l’émulateur et les tests Android.

`LocalGoogleFallbackTest` lance l’application sans clé sur l’émulateur sans services Google, ouvre le Journal depuis le message de repli et utilise sa recherche locale. Ce scénario ne modifie aucun restaurant. Les tests ZIP utilisent un dossier photo/cache isolé et une base en mémoire ; ils ne remplacent pas le carnet installé sur un appareil.

## Exécution sur votre ordinateur

```bash
./gradlew testDebugUnitTest lintDebug assembleDebug assembleRelease assembleDebugAndroidTest --no-daemon
```

Puis, sur un appareil ou émulateur connecté :

```bash
adb devices
./gradlew connectedDebugAndroidTest --no-daemon
```

Les rapports sont dans `app/build/reports/tests/`, `app/build/reports/lint-results-debug.html` et `app/build/reports/androidTests/connected/`. Une clé est inutile pour les tests de données. Le manifeste autorise les fonctions locales sans Google.

En cas de refus de clé ou de quota, utilisez un **projet/clé de test**. Rétablissez votre configuration après l’essai. Consultez le Logcat et Cloud pour distinguer ces causes.

## Fairphone 6 /e/OS 4.0

La présence de microG n’équivaut pas à une validation des SDK Google. `GoogleApiAvailability` peut accepter ou refuser microG selon l’installation. Le chargement du module cartographique et les activités UI Kit peuvent rester incompatibles même si le contrôle initial accepte le service. Resto gère ses erreurs d’initialisation et de requêtes ; aucune garantie n’est donnée concernant un défaut interne du SDK/microG dans une activité externe.

1. Exportez le ZIP de la V1 sur le Fairphone. Notez version /e/OS et version/configuration microG. Gardez la V1 et sa clé de signature.
2. Installez la V1.1 par-dessus avec la même signature, réseau activé.
3. Au premier lancement, observez Carte : carte Google ou message d’indisponibilité. Dans les deux cas, ouvrez Journal, Envies et Stats.
4. Ajoutez manuellement une envie, une visite et une photo ; éditez-les ; partagez une adresse.
5. Exportez un ZIP et restaurez-le. Fermez/reouvrez et vérifiez le carnet.
6. Essayez Rechercher avec Google puis Informations Google Maps. Notez séparément succès de Maps, Autocomplete, coordonnées et Details.
7. Refusez la géolocalisation, désactivez-la puis testez la recherche textuelle. Testez aussi avec une autorisation approximative.
8. Coupez Internet, forcez l’arrêt et relancez ; répétez les fonctions locales. Le cache Google vide ne doit pas masquer les anciennes positions V1.
9. Si votre installation le permet, testez un appareil/émulateur sans services Google pour valider l’écran de repli ; ne supprimez pas microG de votre téléphone quotidien pour cela.
10. Si l’app ferme, relevez **Logcat** dans Android Studio ou `adb logcat` sur votre ordinateur et transmettez l’erreur, en retirant les clés/coordonnées privées. Ne déclarez la compatibilité validée qu’après ce protocole.

La priorité demeure Android standard avec Play Services officiels. Un succès sur un émulateur de données ne valide ni /e/OS ni les services Google réels.
